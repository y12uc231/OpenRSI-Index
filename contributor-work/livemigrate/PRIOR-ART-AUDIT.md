# Live migration: bounded prior-art and verifier audit

Audit date: 2026-09-23. This is a source inspection, not an execution-based reproduction. **This proposal is not the first migration benchmark, first live database benchmark, first safety-aware deployment benchmark, or first multi-agent SRE system.** The current implementation should be described as a one-family prototype until a broader suite is implemented and validated.

## Defensible scope

The proposed evaluation asks whether an agent scaffold can coordinate changes to application, storage, and asynchronous-consumer code while a protected workload exercises old and new versions, delayed messages, backfill, and rollback after new writes. A judge-owned client-operation history makes transient acknowledged data loss, duplicate effects, and semantic corruption count even when the final database looks correct. This combined contract was not identified in the inspected sources below. That is a bounded audit finding, not a claim of global uniqueness.

The research contribution would be the evaluation contract and scaffold-optimization problem. Expand/contract, compatibility matrices, dual writes, idempotent consumers, fencing, migration validation, and rollback are established engineering techniques. A strong baseline should use them. A renamed wrapper or an easier synthetic migration would not justify a novelty claim.

## Other close primary sources

**DBA-Bench is particularly important.** Its 106 PostgreSQL scenarios include 12 business-change cases covering schema evolution and data migration. Workloads remain active; outcome contracts require continuity/integrity, and separate trace rules assess operational safety. Thus “existing benchmarks only check final snapshots” is false. Its paper primarily describes post-state predicates and SQL/management-action safety rules; it does not establish the proposed joint API/storage/consumer implementation and mixed-version message-history contract. This is a paper-level boundary; the full scenario library has not been exhaustively inspected. Reported best automated Safe Pass is 17.9% versus 93.4% for its human reference, which motivates live operations evaluation but is **not** a score or hardness estimate for this proposal. [Paper, §§3–5 and Table 1](https://arxiv.org/html/2607.22165v1); [official artifacts](https://github.com/TanJI-C/DBA-Bench).

**STRATUS already coordinates live SRE mitigation and undo.** Its transactional non-regression argument assumes writer exclusivity, faithful restoration, and bounded transactions. The internal state sequence is hidden from the trajectory used by the guarantee; Table 1 includes a rolling-upgrade example. The proposed task instead keeps client-visible effects during intermediate states in the judge's history, including effects a configuration rollback cannot erase. That is a boundary of the guarantee, not a demonstration that STRATUS would fail this task. Its discussion also recognizes difficulty with application state and external interactions. [NeurIPS 2025 paper, §§3.1–3.3, Table 1 and limitations](https://papers.nips.cc/paper_files/paper/2025/file/47a6e9e2c3019f13ad94a0f259fe4970-Paper-Conference.pdf).

**SREGym and AIOpsLab provide real operational environments.** SREGym includes active microservices, faults, and mitigation verification; correlated, stateful, and recurring failures mean it should not be described as merely checking whether final pods are healthy. The inspected paper/catalog did not establish version-transition code synthesis across application/database/consumer components. AIOpsLab already supplies fault injection, workloads, telemetry, and interaction infrastructure. [SREGym](https://arxiv.org/html/2605.07161v1); [AIOpsLab](https://arxiv.org/abs/2501.06706).

**Evidra Bench already grades release recovery and constrained action paths.** At commit [`d08e8927a3d6e827b70f254f764363c42537459f`](https://github.com/vitas/evidra-bench/tree/d08e8927a3d6e827b70f254f764363c42537459f), [`helm/failed-upgrade`](https://github.com/vitas/evidra-bench/blob/d08e8927a3d6e827b70f254f764363c42537459f/scenarios/helm/failed-upgrade/scenario.yaml) and [`helm/version-rollback`](https://github.com/vitas/evidra-bench/blob/d08e8927a3d6e827b70f254f764363c42537459f/scenarios/helm/version-rollback/scenario.yaml) check Helm release and deployment readiness. [`config-mutation-mid-fix`](https://github.com/vitas/evidra-bench/blob/d08e8927a3d6e827b70f254f764363c42537459f/scenarios/kubernetes/config-mutation-mid-fix/scenario.yaml) injects a second mutation after the first repair and protects evidence/resources. So live drift and action-sensitive verification are already covered. These inspected scenarios do not implement the proposed application-level mixed-version operation semantics.

**SWE migration benchmarks cover substantial code work.** [SWE-Chain](https://arxiv.org/html/2605.14415v1) evaluates sequential dependency upgrades using required and regression tests in target-version containers; each step starts a new agent session from the preceding artifact. [SWE-Refactor Bench](https://arxiv.org/html/2608.23564v1) evaluates whole-repository migrations using audits, fixed behavior tests, and differential verification after collecting the completed tree. [Continuous Benchmark Generation](https://arxiv.org/html/2511.10049v1) derives enterprise service-migration tasks from knowledge and code changes. The inspected evaluation descriptions do not grade client histories throughout a live mixed-version deployment. This is a distinction in evaluation target, not evidence that those migrations are easy.

## Gates before stronger claims

1. Demonstrate at least one trajectory that passes final-state checks but fails the protected temporal oracle, and one conventional safe trajectory that passes both. This validates the claimed measurement difference.
2. Compare a strong expand/contract and rollback-aware scaffold, a matched central agent, and the proposed team under the same total inference/tool budget and information access. Roles must not create an artificial communication handicap.
3. Require migration progress and workload availability; otherwise stopping traffic, leaving the old version forever, or rejecting all writes can trivially avoid corruption. Distinguish allowed transport retries from forbidden duplicate business effects.
4. Freeze seeds and schedules before policy comparison, vary semantic migrations rather than names alone, and test hidden schedules. A single family with renamed fields does not support broad generalization.
5. Report actual local pilot outcomes separately from published adjacent benchmark numbers. No current model failure rate on this exact contract has yet been established by this audit.

If the prototype only repairs a final schema, writes deployment JSON, checks command order, or reproduces a static expand/contract recipe without temporal semantic challenges, the remaining gap collapses and the broader novelty pitch should be withdrawn.

## Current prototype scope

Callbacks execute serially as transactions; traffic interleaves between callbacks, not during them. Bulk table reconstruction in `contract` is allowed and used by the reference. Keeping cents authoritative throughout overlap and reconciling micros at retirement is a valid strategy under this contract. Consequently the prototype does not establish zero downtime, nonblocking DDL, bounded backfill work, or completeness under an operational budget. It tests compatibility of observable semantics across logical interleavings. The single cents-to-micros family may be easy for strong agents; pilot success must be reported without relabeling cases or importing difficulty claims from other benchmarks. Public reference code and schedule variations of one semantic family also permit a scaffold to specialize to the entire family. **Independently authored, withheld migration families are required for a strong scaffold-generalization submission**; this prototype alone does not supply that evidence or an adequate unseen-family split.
