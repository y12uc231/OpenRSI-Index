# Two independent semantic families to validate next

Design notes only: neither family is implemented or evaluated. These change identity and causal-effect semantics, rather than renaming fields or changing a numeric scale. Both still need a reference, independent oracle, negative controls, and model pilots before inclusion in a scored study. Three hand-authored families would establish useful breadth, but would not by themselves establish generalization across repositories or production systems.

## 1. Global request IDs to tenant-scoped IDs

**Task.** Migrate a service's durable request/retry ledger from globally unique client keys to `(tenant_id, client_key)` identity without applying an old accepted operation twice. Each request already contains a tenant, target account and integer delta. The immutable v1 API deduplicates globally by key; its event carries the complete accepted request. The v1 consumer uses a specified domain-separated legacy effect ID. A v2 API and ledger must preserve identity for old requests while eventually admitting the same client key in different tenants.

**Make coexistence logically possible.** While a v1 API can still receive traffic, global key uniqueness remains the published admission rule: a key reused by another tenant or with another payload returns an explicit conflict. The new tenant-collision capability activates only at the published v1-retirement barrier. This restriction is necessary for an unchanged v1 API whose lookup uses only the global key. Claiming unrestricted collisions during coexistence would demand information v1 does not possess. After retirement, delayed v1 messages and retries through v2 remain possible.

**Identity contract.** An accepted pre-retirement operation retains its original legacy effect ID permanently, including retries arriving through v2 after retirement. Newly accepted post-retirement operations use an unambiguous tenant-scoped encoding in a disjoint effect-ID namespace. For example, structured encodings of `["legacy", key]` versus `["tenant", tenant, key]` avoid delimiter/prefix collisions in arbitrary user keys. The evaluator publishes the encoding, not candidate-specific gold outputs. A retry for an imported `(tenant,key)` returns its original operation; reusing that pair with a changed account or delta is a conflict with no effects. A new tenant may use the same raw key after retirement without inheriting the old tenant's receipt.

**Reference strategy.** Add a scoped ledger and an immutable alias from each accepted `(tenant,key)` to its canonical operation/effect ID. During overlap, atomically dual-write the v1 and v2 representations and outbox using legacy IDs. Backfill inserts absent aliases without replacing concurrent accepted records. V2 reads both representations until the completion barrier; after retirement it allocates tenant IDs only for genuinely new pairs. Preserve legacy IDs and payloads in old outbox messages. Both consumers send the stable canonical ID to the sink.

**Oracle and schedules.** An input-derived ledger records admission outcome, immutable payload, and canonical identity. Independently check response/receipt consistency, ledger state after each callback, unchanged outbox history, exact signed account effects, and no cross-tenant effect aliasing. Stress an old request replay during partial backfill; a new API acceptance followed by v1 rollback/retry; a delayed old event after retirement and a new same-key request by another tenant; delimiter-like keys; changed-payload retries; and lost acknowledgements before/after sink commit. The sink is authoritative and idempotent; transport duplicates are allowed, duplicate business effects are not.

**Useful negative control.** A migration that regenerates every legacy operation's effect ID from `(tenant,key)` has a clean final scoped ledger but applies an old delayed operation twice. Another that retains global dedupe forever passes overlap and loses valid post-retirement work. These distinguish identity continuity and progress from final schema correctness.

## 2. Atomic reservation event to allocation plus confirmation

**Task.** Split an old atomic reservation event into two typed events handled by separate allocation and confirmation logic. A reservation has an immutable ID, SKU, quantity, and allocation token. The old event contains all of them; its immutable consumer requests one atomic sink batch containing a stock hold and confirmation. The new producer emits an allocation fragment and a confirmation fragment bound to the same token. Delivery can reorder, repeat, or lose acknowledgements while old and new consumers coexist.

**Compatibility contract.** V1 already ignores unknown event types. During overlap, publish the legacy complete envelope and both new fragments atomically in the outbox. The old consumer handles only the complete envelope; the new consumer handles all three representations. After retirement the complete envelope must stop being required: only split events are delivered, including reordered fragments. This avoids asking an unchanged legacy parser to understand an incomplete fragment. It also prevents using the legacy envelope forever as the entire solution.

**Observable effect semantics.** A valid allocation fragment must produce its stock hold on that delivery. A confirmation may be emitted only after a matching allocation is available and the hold exists, or in a sink batch that establishes the hold before confirming. An early confirmation fragment is durably buffered; it does not authorize an invented allocation. The full legacy event supplies both prerequisites. Logical hold and confirmation IDs are fixed per reservation and shared by all event representations, so a legacy batch interleaved with new fragments cannot double-reserve inventory. The sink checks inventory conservation, correct SKU/quantity/token, and confirmation's prerequisite at every effect prefix. It accepts retries of an identical logical action.

**Reference strategy.** Use transactional producer outboxes. A durable consumer inbox stores fragments by reservation and token, checks agreement, emits the allocation action promptly, and emits confirmation only once prerequisites are present. Retried action intents retain their canonical effect IDs; sink deduplication resolves lost acknowledgements. Legacy complete messages follow the same canonical actions. The consumer may write its own inbox/outbox tables but cannot edit the judge's inventory/effect ledger. Allowed persistence and transaction boundaries must be explicit; the first family's read-only consumer API is insufficient for this task.

**Oracle and schedules.** Judge-known initial stock and accepted reservations determine correct quantities. The judge records every physical hold/confirmation independently of candidate state. Include confirmation-before-allocation, duplicate allocation around a lost acknowledgement, legacy complete delivery between new fragments, restart with only the early fragment persisted, several SKUs and tokens interleaved, and delayed legacy messages after retirement. Progress checks require immediate allocation when its fragment arrives and eventual confirmation once both prerequisites have been delivered. Do not introduce cancellation or retroactive amendments in the first version: without a published sequence/watermark contract, they can create impossible demands to foresee a not-yet-delivered revocation.

**Useful negative control.** A final-state aggregator can reconstruct correct reserved totals but confirm before a matching hold; another treats the old complete event and new allocation as different identities and double-reserves. Both must fail the protected history oracle even if a later compensation restores final inventory.

## Study implications

All arms receive the complete applicable contract, immutable legacy implementation, normal inspection tools, and equal total inference/tool budgets. Ownership roles organize work rather than hiding necessary information. Use an explicit conventional compatibility scaffold and a central agent; do not make independent one-call workers the sole baseline.

These are still compact, solvable software tasks with simple reference strategies. Strong agents may pass them. Pilot all declared families, report successes and failures, and do not increase difficulty selectively after observing one model's outcome. Once reference solutions are published, schedule variants alone are weak protection against specialization. A strong OpenRSI claim needs fresh authored semantic families withheld from scaffold development, with the split fixed before outcomes and all reference feasibility checks run under the same contract.
