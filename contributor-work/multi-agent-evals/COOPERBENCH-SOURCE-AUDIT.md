## Source-level execution and evaluator audit

The [dataset README](https://github.com/cooperbench/CooperBench/blob/63b9d44d9f39a02fccf5bf0052db48a917a011fd/dataset/README.md) distinguishes source feature descriptions, public gold implementation patches, feature-specific test patches, and a combined oracle patch. Feature gold patches need not merge; the combined patch is the resolved oracle. The dataset claims all 199 features validated on amd64/arm64. Before adoption, run the pinned oracle/base checks ourselves; README assertions are not our verification.

The [flash manifest](https://github.com/cooperbench/CooperBench/blob/63b9d44d9f39a02fccf5bf0052db48a917a011fd/dataset/subsets/flash.json) was parsed without importing repository code: exactly **50 feature pairs, 20 base tasks, 11 repositories**. It is a public development subset, not a secret holdout. Pair-level splits can share a base PR or feature, so a fresh OpenRSI split must group by base task or preferably repository. Do not develop on flash and call overlapping pairs a generalization test.

The [team runner](https://github.com/cooperbench/CooperBench/blob/63b9d44d9f39a02fccf5bf0052db48a917a011fd/src/cooperbench/runner/team.py) uses separate agent containers, a shared Redis task list, a shared `/workspace/shared` volume, and optional shared git. The [Docker agent environment](https://github.com/cooperbench/CooperBench/blob/63b9d44d9f39a02fccf5bf0052db48a917a011fd/src/cooperbench/agents/mini_swe_agent_v2/environments/docker.py) launches a container per agent. This is stronger workspace separation than unsandboxed local tools, but **not sealed evaluation**: default networking is a normal Docker bridge, and no default CPU/memory limits appear in that environment. Only intended coordination state should be shared in an OpenRSI wrapper.

The [evaluator](https://github.com/cooperbench/CooperBench/blob/63b9d44d9f39a02fccf5bf0052db48a917a011fd/src/cooperbench/eval/sandbox.py) reads test patches on the controller, starts a fresh evaluation sandbox, removes test-path changes from submitted patches, and injects evaluator-owned tests into `/patches`. It evaluates both feature suites. Current policy is **identical patch short circuit → naive merge → lead-only fallback when merge/input application fails**. A clean merged tree that fails tests does not receive fallback credit. Preserve this exact policy for comparable controls, or declare any new single-integrated-patch protocol a distinct evaluation.

The [Docker evaluator backend](https://github.com/cooperbench/CooperBench/blob/63b9d44d9f39a02fccf5bf0052db48a917a011fd/src/cooperbench/eval/backends/docker.py) creates a fresh container without mounting the Work checkout, but has no explicit network disabling, resource caps, read-only test mount, or hostile-patch security boundary. `sandbox.py` judges exit status plus parsed test-output counts. A representative [Click runner](https://github.com/cooperbench/CooperBench/blob/63b9d44d9f39a02fccf5bf0052db48a917a011fd/dataset/pallets_click_task/task2068/runner.sh) applies candidate/test patches then performs editable installation and runs pytest. Thus source changes can affect build/test execution; test filename filtering alone is not a proof against grader manipulation. Public gold patches/tests can also be fetched with the default network.

For OpenRSI, put dataset truth, scorer, manifest, image digests, merge policy and budgets in evaluator-owned paths outside Work; serve candidate workers only base repositories/descriptions and allowed development tests. Disable arbitrary network during judged execution except a controlled inference endpoint and coordination services; disallow test/build-runner redirection and grade with integrity-checked evaluator assets. Collect scores on the controller rather than accepting worker-written `eval.json`. Define invalid/tampered outputs and infrastructure errors explicitly. These are adaptation work still required, not capabilities already demonstrated by this audit.

## Candidate research contract: adaptive evidence-based joint verification

**Research question:** At a fixed total inference and execution budget, can an agent discover a coordination policy that increases both-features-pass probability by identifying cross-agent interface dependencies, attaching executable evidence to proposed changes, and allocating joint integration checks only where dependency risk warrants them?

This is an OpenRSI research improvement task: the outer research agent edits a reusable coordinator/prompt/routing/verification policy for two frozen coding workers, then tests policy candidates. It does not submit hand-solved patches for test instances. Candidate artifact: policy package with a stable hook interface for initial task decomposition, evidence exchange, dependency changes, verification scheduling and final integration. No task IDs or reference solutions in the policy.

**Fixed components:** one pinned open-weight model checkpoint/tokenizer/precision, two worker roles, container images by digest, source/base commits, evaluation tests, split manifest, total model input/output or equivalent serving budget, total wall-clock/CPU budget, number of tool calls/checks, and model context limit. All policy overhead and helper model calls count against the same budget. A provisional reproducibility model is Qwen3-Coder-30B-A3B-Instruct; its old 13.3% score is motivation only. A smaller current 9B Qwen can be considered after an equal-budget pilot, without swapping models mid-comparison.

**Allowed research:** decide when to request a symbol/interface contract; require file/symbol references and locally executable checks; identify changed assumptions; choose which agent reruns which joint check; revise coordination prompts or compact shared memory; design uncertainty/risk estimates. **Protected:** worker weights, test suites, merger, scorer, hidden asset access, total budget, success criterion. Do not award points for the number of messages/contracts or self-reported task completion.

**Primary score:** paired held-out feature-pair success improvement versus the frozen strongest implemented baseline at the same total budget. Success means both feature suites pass under the pinned merger. Report absolute success and paired bootstrap uncertainty too. Secondary diagnostics: merge conflicts, clean-merge semantic failures, no-change regressions, tokens, verification calls and completion latency. Require budget compliance and report every prespecified pair; infrastructure failures are separately retried under a bounded unchanged policy and never quietly dropped from a favorable denominator.

**Essential controls:** equal-budget solo; coop+git; current team without typed protocol; fixed contract-first protocol; unconditional verification at every checkpoint; candidate adaptive verification. The decisive comparison is against current **team-no-protocol**, not an intentionally weak chat-only baseline. Upstream already publishes [Qwen contract-first experiment data](https://huggingface.co/datasets/CooperBench/qwen35-9b-contract-first-coop-random-50) alongside plan-first, late-sync, question-first and other protocols. Generic “contracts improve teamwork” is already explored. The potential contribution is learning a robust evidence/verification allocation method with held-out transfer, beyond these specific baselines.

**Split and readiness:** use the public 50-pair flash subset for feasibility only. Freeze a task/repository-grouped dev and final split before policy optimization, checking no shared base task or feature. Run combined-oracle and untouched-base checks for every eligible pair; if a pair fails infrastructure validation, exclude it before model comparisons and publish the fixed exclusion reason. The audited OpenRSI catalog has no equivalent multi-agent code-integration policy task, but this is catalog distinctiveness—not a globally novel benchmark claim.

## Concrete commands and resource gates

These commands are inspected interfaces, **not commands executed in this audit**. From the pinned source checkout after dependency/environment preparation:

```sh
uv sync
cooperbench run -n baseline-team-flash --backend docker --setting team -s flash -c 2 -a mini_swe_agent_v2 -m MODEL --agent-config frozen-config.yaml --no-auto-eval
cooperbench eval -n baseline-team-flash --backend docker -c 2
```

Confirm flags with the pinned CLI before running. The source's [mini-SWE coop config](https://github.com/cooperbench/CooperBench/blob/63b9d44d9f39a02fccf5bf0052db48a917a011fd/src/cooperbench/agents/mini_swe_agent_v2/config/coop.yaml) has 100 steps / $3 per-agent defaults; dollar limits are not sufficient for a locally served model and need a real token/serving budget. The [local Qwen guide](https://github.com/cooperbench/CooperBench/blob/63b9d44d9f39a02fccf5bf0052db48a917a011fd/docs/QWEN_LOCAL.md) documents a vLLM endpoint and Qwen3.5-9B tool calling through the Claude Code adapter; it does not establish 30B hardware requirements. The [Codex adapter](https://github.com/cooperbench/CooperBench/blob/63b9d44d9f39a02fccf5bf0052db48a917a011fd/src/cooperbench/agents/codex/adapter.py) has an Azure path with zeroed token/cost telemetry, which cannot directly enforce our fixed-inference-budget contract.

Practical prerequisites are Docker-capable CPU/RAM/storage, Redis, pinned images and a frozen inference endpoint. Local worker inference needs appropriate GPU capacity; no particular GPU count, model-fitting claim, or round runtime is established. The user's GPU model/count/VRAM, CPU cores/RAM and supported single-node execution environment are still missing. Run a 5–10-pair warm-cache feasibility pilot to measure median/p95 pair duration, memory, model tokens and container startup failure rate. Fifty pairs times pair cost is only a budgeting calculation, not a runtime prediction; the source documents failures at concurrency 10 and stable small runs at concurrency 3. A credible OpenRSI loop should fit several candidate/control rounds within the available research budget, which remains unmeasured.

**Status:** scientifically actionable candidate research contract, with mature public assets and stronger evidence than RelayRepair. Not yet a formal proposal or a ready-to-run sealed OpenRSI task. Missing gates are current frozen-model baseline reproduction, infrastructure validation, protected evaluator adaptation, grouped split, budget enforcement and user hardware metadata.
